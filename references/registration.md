# Регистрация и контекст выполнения

Источники: [регистрация](https://bia-technologies.github.io/yaxunit/docs/features/test-registration/),
[организация тестов](https://bia-technologies.github.io/yaxunit/docs/getting-started/structure/).
Версия примеров указана в [совместимости](compatibility.md).

## Модуль и тесты

Тесты размещаются в собственных, не заимствованных общих модулях тестового расширения.
Расширение может содержать движок или подключаться отдельно.

По рекомендации YAxUnit одному проверяемому модулю соответствует один тестовый общий
модуль. Сначала найди его и дополни; при отсутствии создай новый. Методы одного модуля
проверяй в соответствующем тестовом модуле; тесты модуля объекта и модуля менеджера
по умолчанию размещай отдельно. Сложившиеся соглашения проекта имеют приоритет.

Имя выбирай по соглашениям проекта. Если их нет, используй рекомендуемую YAxUnit
схему: префикс типа объекта, имя объекта и суффикс типа проверяемого модуля.

| Проверяемый модуль | Пример имени тестового общего модуля |
|---|---|
| Общий модуль `ОбщегоНазначения` | `ОМ_ОбщегоНазначения` |
| Модуль объекта справочника `Пользователи` | `Спр_Пользователи_МО` |
| Модуль менеджера справочника `Пользователи` | `Спр_Пользователи_ММ` |
| Модуль набора записей регистра сведений `Настройки` | `РС_Настройки_НЗ` |

Остальные префиксы см. в [организации тестов YAxUnit](https://bia-technologies.github.io/yaxunit/docs/getting-started/structure/).
Это рекомендация по организации, а не условие обнаружения тестов движком.
Не переименовывай существующие модули ради этой схемы; `Тест_...` не является требованием YAxUnit.

Предопределенная процедура `ИсполняемыеСценарии()` и тестовые процедуры должны
быть экспортными. Движок вызывает регистрацию до исполнения тестов: здесь
перечисляй сценарии и настройки, но не создавай записи, файлы, объекты-заглушки
и не обучай Мокито. Подготовку вынеси в тест или обработчик жизненного цикла.

```bsl
// Регистрирует серверные проверки расчета.
Процедура ИсполняемыеСценарии() Экспорт
	
	ЮТТесты.ДобавитьТестовыйНабор("Расчет");
	ЮТТесты.ДобавитьСерверныйТест("СуммаСУчетомСкидки")
		.СПараметрами(100, 0, 100)
		.СПараметрами(100, 25, 75);
	
КонецПроцедуры
```

Здесь `СуммаСУчетомСкидки` - имя тестовой процедуры с тремя параметрами.
Наборы группируют тесты; теги через `Тег(...)` позволяют их отбирать.

## Клиент и сервер

- `ДобавитьТест(...)` использует все доступные контексты модуля.
- `ДобавитьКлиентскийТест(...)` и `ДобавитьСерверныйТест(...)` ограничивают
  выполнение соответствующей стороной.
- `СПараметрамиНаКлиенте(...)` и `СПараметрамиНаСервере(...)` задают контекст
  конкретного набора параметров.

Выбор регистрации не включает контекст в метаданных автоматически. Проверь
свойства общего модуля и доступность проверяемого кода. В смешанном модуле
отделяй недоступные стороне участки директивами препроцессора; директивы
модуля формы не переноси в общий модуль. Серверный тест не требует разрешать
произвольный вызов его методов с клиента через `ServerCall`.

## Настройки и параметры

Настройка перед добавлением наборов относится к модулю, после добавления набора -
к набору, после теста - к тесту. У параметризованного теста отдельные варианты
тоже могут иметь свои настройки. Учитывай текущее положение цепочки, чтобы
случайно не изменить соседний тест.

`СПараметрами(...)` принимает до десяти параметров. Значения должны подходить
для передачи движком; в частности, учитывай сериализацию между контекстами.
В регистрации передавай простые исходные значения, а несериализуемые объекты
создавай во время исполнения. Подробности: [варианты](variants.md).

## Файлы и XDTO

Для переносимых файлов используй существующие зависимости проекта и
`ЮТТесты.ЗависитОт().ФайлыПроекта(...)`, для схем XDTO -
`ЗависитОт().ФабрикаXDTO(...)`. Получение объявленной зависимости выполняется
через `ЮТест.Зависимость(...)`: сигнатуры и порядок получения сверь с версией.
Не закрепляй абсолютный путь своей машины в тесте.

Запуск и отладку используй в уже настроенном окружении проекта. Если окружение
не подготовлено, обозначь это отдельно от корректности регистрации;
создание базы и настройка поставки движка не входят в обычное написание теста.

## Quick Start

1. Прочитай целевой метод и только те зависимости, которые реально влияют на
   выбор стратегии тестирования.
2. Выбери одну основную форму теста по таблице ниже.
3. Подготовь сценарии: happy path, границы, невалидные данные, явный
   ошибочный путь.
4. Переиспользуй существующий тестовый модуль или создай новый из шаблонов в
   `assets/`.
5. Зарегистрируй каждый тест в `ИсполняемыеСценарии()` и перепроверь чеклист в
   конце файла.

Не спрашивай лишних подтверждений для обычных методов. Для сложных методов
сначала дай пользователю план.

## Загружай references только по необходимости

- `references/assertions.md` - обычные утверждения YAxUnit, цепочки, типы,
  исключения.
- `references/db-assertions.md` - `ЮТест.ОжидаетЧтоТаблицаБазы(...)` и когда
  ее сочетать с `ЮТЗапрос.Запись`.
- `references/variants.md` - `.СПараметрами(...)`, `ЮТест.Варианты()` и
  `ДобавитьКомбинации()`.
- `references/mockito.md` - канонический API Мокито и проверки вызовов.
- `references/interception.md` - `&Вместо`, self-call и borrowed-модули.
- `references/fixtures.md` - ручные in-memory fixtures без реальной ИБ.
- `references/test-data-builders.md` - `ЮТест.Данные()`, `КонструкторОбъекта`,
  `Фикция*`, `КонструкторДвижений`, XDTO.
- `references/http-and-sql-stubs.md` - `HTTPСервисЗапрос()`, `ADORecordSet()`
  и когда их брать вместо самодельных заглушек.
- `references/templates.md` - когда и как применять шаблоны из `assets/`.
- `references/anti-patterns.md` - частые ошибки и короткие правила `Do / Don't`.

Если при этом редактируешь BSL-код, дополнительно соблюдай профильные BSL-скиллы
по стилю и переносам строк, а не дублируй их правила здесь.

## Шаг 1: Прочитать метод

Если пользователь дал имя модуля и метода, сначала найди:

```text
CommonModules/<ИмяМодуля>/Ext/Module.bsl
```

Прочитай:

- целевой экспортный метод;
- вызываемые им приватные методы в том же файле;
- экспортные зависимости из других модулей, только если от них зависит выбор
  формы теста, данных или перехвата.

Если пользователь вставил код напрямую, анализируй его как источник истины.

## Шаг 2: Выбрать стратегию

| Что видишь | Что делать |
|---|---|
| Только параметры, локальные переменные и чистые вычисления | Тестируй напрямую и читай `references/assertions.md` |
| Один и тот же алгоритм нужно прогнать на фиксированном наборе входов | Используй `.СПараметрами(...)`, читай `references/variants.md` |
| Нужны динамические комбинации входов или цикл по перечислениям | Используй `ЮТест.Варианты()` и `ДобавитьКомбинации()`, читай `references/variants.md` |
| `РегистрыСведений.X.СоздатьНаборЗаписей()`, `.Добавить()`, `.ДополнительныеСвойства`, `.ОбменДанными` без `.Записать()` | Создавай реальный объект в памяти и проверяй его, читай `references/fixtures.md` |
| Нужно управлять экспортным методом другого модуля | Используй Мокито, читай `references/mockito.md` |
| Нужен self-call, реальные параметры через `Вызовы()` или borrowed-модуль | Используй `&Вместо`, читай `references/interception.md` |
| Метод меняет ИБ как наблюдаемый результат | Проверяй наличие через `ЮТест.ОжидаетЧтоТаблицаБазы(...)`, заполнение через обычные assertions, читай `references/db-assertions.md` |
| Нужны запрос HTTP-сервиса, `ADO.RecordSet`, объект ИБ или XDTO | Бери `ЮТест.Данные()`, читай `references/test-data-builders.md` и `references/http-and-sql-stubs.md` |
| `Константы.X.Получить()` или `Перечисления.X.ЗначениеПеречисления` | Обычно используй напрямую; объявляй метод нетестируемым только если дефолт ломает смысл теста |
| `ТранзакцияАктивна()`, `ТекущаяДата()` и другие глобальные функции без модуля | Не обещай мок. Управляй состоянием теста напрямую |

Дополнительные правила:

- Выбирай одну основную форму теста и смешивай техники только когда это
  действительно нужно.
- Делегирующий метод, который только выбирает ключ и передает вызов дальше,
  обычно требует один тест: выбран правильный путь и вызов дошел до делегата.
- Если код читает поля через точку `Объект.Поле.Ключ`, используй `Структура`,
  а не `Соответствие`.
- Прежде чем назвать метод нетестируемым, проверь существующие `&Вместо` в
  расширении, `ЮТест.Данные()` и отдели операции в памяти от реальных
  обращений к ИБ.

## Шаг 3: Определить сценарии

Для каждого метода подготовь четыре категории:

1. Happy path.
2. Граничные случаи.
3. Невалидные данные.
4. Ошибочный путь, если метод сам формирует диагностическое исключение.

Минимальные правила:

- Если несколько сценариев отличаются только входными данными и ожидаемым
  результатом, сворачивай их в `.СПараметрами(...)` или `ЮТест.Варианты()`.
- Для каждого параметра объектного типа дай хотя бы один тест с
  `Неопределено` или неправильным типом.
- Если метод обращается к свойствам структуры, проверь структуру без нужного
  свойства.
- Если ожидается положительное число, проверь `0` или отрицательное значение.
- Если строка обязательна, проверь `""` и строку из пробелов.
- Если коллекция обязательна, проверь пустую коллекцию.
- Если метод должен выбросить исключение, используй
  `.ВыбрасываетИсключение("")` для любого текста либо
  `.ВыбрасываетИсключение("фрагмент")` для конкретного сообщения.
- Если метод должен отработать штатно без исключения, допускается
  `.НеВыбрасываетИсключение()`.
- Для параметров без `Знач` проверяй и возвращаемый результат, и видимую
  вызывающему коду мутацию.
- Именуй тесты по схеме `<ЧтоТестируем>_<Условие>_<ОжидаемыйРезультат>`.

## Шаг 4: Найти или создать тестовый модуль

Сначала проверь существующие тестовые модули:

```text
CommonModules/*Тест*
```

Правила:

- Если паттерн именования уже есть, следуй ему даже если он не совпадает с
  общим советом ниже.
- Если тестового модуля нет, используй имя `Тест_<ИмяТестируемогоМодуля>`.
- Если модуль существует, добавляй новые тесты в конец файла и не забудь
  дописать `ЮТТесты.ДобавитьТест(...)` в `ИсполняемыеСценарии()`.
- Каждая тестовая процедура и `ИсполняемыеСценарии()` должны быть `Экспорт`.
- Если модуль отсутствует, используй шаблоны из `assets/`:
  `test-common-module.bsl.template` и `test-common-module.xml.template`.
- Для заимствованного стороннего модуля под `&Вместо` используй
  `adopted-common-module.xml.template` и `instead-stub.bsl.template`.

Подробные placeholders и порядок подстановки см. в `references/templates.md`.

## Шаг 5: Написать тесты

Базовые правила:

- Один тест - один осмысленный сценарий.
- Если несколько тестов используют одни и те же данные, вынеси их в приватные
  функции без `Экспорт`.
- Если фабричный метод сам идет в ИБ, не зови его в чистом юнит-сценарии:
  собери минимальную структуру вручную или через `ЮТест.Данные()`.
- Для параметров по ссылке проверяй и возвращаемый результат, и измененную
  переменную.
- Для Мокито, `&Вместо`, assertions ИБ и builders используй профильные
  `references/*`, а не дублируй паттерны в коде теста.
- Для `Мокито.Обучение(...)`: первый вызов в тесте делай без второго параметра,
  каждый следующий вызов обучения в том же тесте делай с `Ложь` вторым параметром,
  иначе предыдущие обучения будут сброшены.

```bsl
Мокито.Обучение(ИПСлужебный).Когда("СтандартнаяОбработка").Вернуть(Ложь);
Мокито.Обучение(ИПСлужебный, Ложь).Когда("ПриЗапросеДанных").Пропустить();
Мокито.Обучение(ИПОбработкаВходящихСобытий, Ложь).Когда("ДанныеИзКаталога").Вернуть(ПустыеДанные);
Мокито.Обучение(ИПОбработкаВходящихСобытий, Ложь).Когда("ДанныеИзСервиса").Вернуть(ПустыеДанные);
Мокито.Прогон();
```

Только как крайний случай добавляй тестовый прокси к приватному методу.
По умолчанию приватная логика должна покрываться косвенно через экспортный
метод.

## Сложные и нетестируемые методы

Сначала покажи пользователю план, а не пиши код сразу, если:

- нужно 3 и более разных заглушки;
- есть `Попытка/Исключение` с несколькими поведенческими ветками;
- нужно заимствовать больше одного метода из стороннего модуля;
- комбинация Мокито, `&Вместо`, проверок ИБ и платформенных глобальных функций
  неочевидна.

Сообщай, что метод нетестируем в юнит-формате, только если после проверки
существующих `&Вместо`, `ЮТест.Данные()` и точек изоляции все еще остается
неперехватываемый вызов, без которого сценарий не имеет смысла. В таком
случае:

- кратко объясни причину;
- предложи следующий тестируемый метод или переход к интеграционному тесту.

## Финальный чеклист

- [ ] Каждая тест-процедура добавлена в `ИсполняемыеСценарии()`
- [ ] Каждая тест-процедура объявлена с `Экспорт`
- [ ] `ИсполняемыеСценарии()` объявлена с `Экспорт`
- [ ] Есть happy path
- [ ] Покрыты граничные случаи
- [ ] Для каждого объектного параметра есть `Неопределено` или неправильный тип
- [ ] Для параметров без `Знач` проверено изменение переменной после вызова
- [ ] Выбрана правильная основная форма теста
- [ ] Нет устаревшего API Мокито
- [ ] Если создавался новый тестовый модуль, обновлен `Configuration.xml`
- [ ] Если заимствовался сторонний модуль под `&Вместо`, созданы его `.xml`,
      `.bsl` и обновлен `Configuration.xml`
- [ ] Если метод пишет в ИБ, наличие и заполнение проверены раздельно
- [ ] Если что-то выглядит подозрительно, перечитан `references/anti-patterns.md`
- [ ] Для сложного метода план согласован с пользователем
